# CHIP-8 エミュレータ仕様（Part 1）

Rust 入門記事の骨格を、Racket 実装向けに要約した仕様である。[1]
コードは置かない。命令の意味の正本は [CHIP-8 命令セット](CHIP-8-命令セット.md) とする。[2]

出典: Aqua-218『「CHIP-8って何？」から始めるエミュレータ開発 Part1』（Qiita、2025-12-09、最終更新 2025-12-11）。[1]

## 前提

CHIP-8 は 1970 年代のインタープリタ型仮想マシンである。[1]
実在 CPU ではなく、GB / ファミコンより小さい入門用 VM、というのが動機である。[1]
言語は Rust でも Racket でもよく、持っていくのは状態の切り方と命令の分解である。

## 機械の定数

| 項目 | 値 |
|---|---|
| メモリ | 4096 バイト（4KB） |
| 画面 | 64×32、モノクロ（点灯 / 消灯） |
| 汎用レジスタ | V0–VF、各 8 bit。VF は衝突・キャリー用フラグ |
| インデックス | I、16 bit |
| プログラムカウンタ | PC、16 bit |
| スタック | 16 段、戻りアドレス用。SP がその深さ |
| タイマ | delay と sound。本家は 60Hz で減る |
| キー | 16 個（0–F） |

フォントは数字 0–F の 16 文字、各 5 バイト、計 80 バイト。[1]

## メモリマップと初期化

- `0x000`–`0x1FF` はインタプリタとフォント予約。フォントを先頭へ置く。[1]
- プログラムは `0x200` から。PC の初期値は `0x200`。[1]
- 状態は 1 つの機械にまとめる: メモリ、画面バッファ、V、I、PC、スタック、SP、delay、sound。[1]

不変更新か、レジスタだけ破壊的更新かは実装前に決める。CPU・画面・タイマを別オブジェクトに散らさない。

## 実行の形

常に Fetch → Decode → Execute。[1]

1. Fetch: 命令は常に 2 バイト。`mem[PC]` を上位、`mem[PC+1]` を下位として 16 bit オペコードにし、PC を 2 進める。[1]
2. Decode: オペコードを 4 ニブルに分ける。例 `0x6108` なら op=`6`、x=`1`、y=`0`、n=`8`、nn=`0x08`、nnn=`0x108`。[1]
3. Execute: ニブルの組で命令を選ぶ。未知オペコードは止める（記事の画面出力より、テストが落ちる方がよい）。

cycle は「命令 1 つ + タイマ減算」である。[1]
記事は毎サイクルでタイマを 1 減らす。これは Part 1 の単純化で、本家は CPU と 60Hz が別である。[1]
目安は「1 秒に約 700 命令、タイマは 60Hz」。最初は記事どおり 1 関数、次に「命令 N 回につきタイマ 1 回」に分ける。境界だけ cycle に揃えると、あとで GUI のタイマに載せやすい。

## Part 1 で実装する命令

画面が出る最小集合だけ先に書く。[1]
キー入力・全命令・ウィンドウはこの範囲外である。[1]

| オペコード | 名前 | この仕様での意味 |
|---|---|---|
| `00E0` | CLS | 画面をすべて消灯 |
| `00EE` | RET | スタックから戻りアドレスを取り、PC に戻す。SP を下げる。溢れ検査を先に入れる |
| `1NNN` | JP | PC を nnn にする |
| `2NNN` | CALL | 現在の PC を積み、PC を nnn にする。溢れ検査を先に入れる |
| `6XNN` | LD Vx, nn | Vx に nn を入れる |
| `7XNN` | ADD Vx, nn | Vx に nn を足す。8 bit でラップアラウンド（キャリーは立てない） |
| `ANNN` | LD I, nnn | I に nnn を入れる |
| `DXYN` | DRW | 下記 |

## 描画 `DXYN`（本丸）

順は次の 5 つ。[1]

1. 開始座標は `Vx % 64`、`Vy % 32`。VF を 0 にする。
2. I から N バイト読む。
3. 各バイトは MSB から 8 画素。
4. 既に点灯している画素を消したら VF=1。画素は XOR。
5. 画面端ではクリップする（折り返さない）。座標の剰余は開始位置だけ。

衝突（消えたら VF=1）はゲーム ROM の当たり判定そのものなので、省略しない。[1]
画面表現は「64×32 の真偽の二次元」が記事と同じ思考になる。ビットパックは後でよい。
端末の █ / 空白は、GUI 前のデバッグ手段として使う。[1]

## テスト（Part 1）

ROM ファイルは読まない。[1]
顔スプライト 5 バイトと、LD / LD I / DRW をメモリにベタ書きし、cycle を数回回して端末に画面を出す。[1]
記事のテストはスプライトを `0x200`、命令本体を `0x205` に置き、PC を `0x205` から始める。[1]
第一号テストは「数サイクル後、指定画素が点灯している」で足りる。GUI より先にこれを通す。

## Racket へ持っていく 6 点

1. 機械状態を 1 か所に置く
2. 定数とメモリマップを先に固定する（4096、64×32、フォント先頭、PC=`0x200`）
3. Fetch を 2 バイト結合に固定する
4. ニブル分解してから命令を選ぶ（命令が増えたら、この分解がマクロの入力仕様になる）
5. `DXYN` の 5 手順をそのまま移植する
6. 最小テストをベタ書き ROM で始める

メモリは長さ 4096 のバイト列が自然（ROM 読みと相性がよい）。
画面と CPU ループを後で分けるなら、共有バッファ＋ UI 側描画、という境界だけ先に意識する。

## 持っていかないもの

- Rust の所有権・配列コピーの話
- 毎サイクルでタイマを 1 減らす精度（仕様としては不正確）
- 画面へのデバッグ出力を本番ログにする設計
